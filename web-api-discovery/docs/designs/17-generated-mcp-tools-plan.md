# The generated MCP server lists its tools

- Issue: https://github.com/IntelliTect-dev/Multiplex/issues/17
- PR:    (filled in at Phase 7)
- Slug:  17-generated-mcp-tools

## Overview

A wrapper generated by `generate-wrapper.js` has an MCP entry point
(`McpProgram.cs`) that calls `WithToolsFromAssembly()`, but nothing in the
project is marked `[McpServerToolType]` / `[McpServerTool]`. The server starts
and lists no tools. Measured before any change, on a wrapper generated from
`rest-3endpoints.har` and started over stdio:

```
tools/list -> {"code":-32601,"message":"Method 'tools/list' is not available."}
```

The emitted smoke test (`Mcp.Tests.ps1`) reads the source for `[Description]`
attributes, so it passes anyway. The generated project also pins
`ModelContextProtocol` `0.4.1-preview.1`; the host (`src/Multiplex.Web`) is on
the 2.4.0 line.

## Approved design

Taken from the issue; the choices it leaves open are listed under
**Judgement calls**.

### 1. One SDK version line

`emitCsproj` pins `ModelContextProtocol` to the host's version (2.4.0). That
package is the one a stdio server needs: it carries `AddMcpServer`,
`WithStdioServerTransport` and `WithToolsFromAssembly`; `.Core` has no hosting
extensions and `.AspNetCore` is the HTTP transport. 2.4.0 requires
`Microsoft.Extensions.Hosting.Abstractions` and
`Microsoft.Extensions.Logging.Abstractions` `>= 10.0.14`, so the two
`Microsoft.Extensions.*` pins move from 10.0.0 to 10.0.14 -- left alone, restore
fails with NU1605 (package downgrade).

A test pins the generated version to the host's csproj, so the two cannot drift.

### 2. A tool class per site

New generated file `src/<Name>/<Name>Tools.Generated.cs`:

```csharp
[McpServerToolType]
public sealed partial class <Name>Tools
{
    public <Name>Tools(<Name>ToolSession session) { ... }

    [McpServerTool(Name = "get_users_by_id", ReadOnly = true, Destructive = false, Idempotent = true, OpenWorld = true)]
    [Description("Gets users by id. Sends GET /api/users/{id} to https://api.example.com. Returns an object with: active, id, name.")]
    public Task<UserResponse> GetUsersByIdAsync(
        [Description("The id in /api/users/{id}.")] int id,
        CancellationToken ct = default)
        => _session.RunAsync(client => client.GetUsersByIdAsync(id, ct));
}
```

- One tool per generated client method, GraphQL included (`graphql`).
- The wire name is set explicitly (`snake_case` of the client method without
  `Async`), so it does not depend on an SDK default.
- The description is derived from the operation: what it does, the HTTP method
  and path template, the site, the response's field names, and for a write what
  calling it does to the site.
- Property names verified against the restored 2.4.0 package's XML docs:
  `Name`, `ReadOnly`, `Destructive`, `Idempotent`, `OpenWorld`. SDK defaults are
  `Destructive = true`, the rest `false` except `OpenWorld = true`; every tool
  sets all four explicitly.

### 3. Hints from the HTTP method and the operation

| Operation | ReadOnly | Destructive | Idempotent |
|---|---|---|---|
| GET, HEAD, OPTIONS | true | false | true |
| POST | false | false | false |
| POST whose path names a change or removal (`/delete`, `/cancel`, `/update`, ...) | false | true | false |
| PUT | false | true | true |
| PATCH | false | true | false |
| DELETE | false | true | true |
| GraphQL (query or mutation, unknown) | false | true | false |
| anything else | false | true | false |

### 4. The session is read at the first tool call

New template `ToolSession.cs.tmpl` -> `<Name>ToolSession`, a singleton every
tool call goes through:

- reads `ISessionStore` at the first call, not at server start, and caches only
  a session it found -- so signing in while the server runs needs no restart;
- never calls the authenticator (which reads `Console.In` and writes
  `Console.Out`); a missing session is the tool call's error;
- turns the failures a model can act on -- no session, session expired,
  throttled, blocked, an HTTP error, a response that is not the expected JSON --
  into `McpException`, whose message the SDK passes to the client. Any other
  exception stays generic. The message carries no cookie and no store path.

`McpProgram.cs.tmpl` drops the eager `SessionCredentials` and client
registrations and registers the session instead.

### 5. A smoke test that starts the server

- `csharp/tests/pester/McpStdio.ps1.tmpl` -- a minimal MCP stdio client
  (`Invoke-McpStdioSession`): start the built `.dll`, `initialize`,
  `notifications/initialized`, the requests it is given; stderr drained, every
  read under a deadline, the process stopped by its own handle.
- `Mcp.Tests.ps1.tmpl` -- builds the wrapper, starts it, and asserts
  `tools/list` returns exactly the tools the generator baked in, each with a
  description and its hints, and that stdout carried only JSON-RPC. The expected
  list is derived from the endpoint list, not read back from the emitted tool
  class, and "at least one" is asserted on its own.
- `web-api-discovery/tests/generated-mcp-server.Tests.ps1` -- generates from a
  new CRUD fixture (`rest-crud.har`: GET, POST, PUT, PATCH, DELETE), builds with
  0 warnings, and asserts literal names, hints, input schemas, the no-session
  `tools/call` error, and a falsifier: with the generated tool class removed the
  emitted smoke test fails.
- `scripts/codegen/mcp-tools-emit.test.js` -- zero-dep unit tests for naming,
  hints and descriptions.

## Judgement calls

Made without the owner; each is in the hand-off report.

1. **POST is additive unless its path says otherwise.** The issue says "POST
   additive = not idempotent". A POST to `/items/42/delete` is not additive, so
   a path word naming a change or removal flips `Destructive` to true. A POST
   the word list does not recognise is still reported as additive.
2. **PUT is destructive and idempotent; PATCH is destructive and not
   idempotent.** Both replace existing data, which the SDK's own definition of
   "destructive" covers ("false if the tool performs only additive updates").
3. **GraphQL gets one passthrough tool** with the conservative hints, because
   one endpoint carries both queries and mutations.
4. **Every client method gets a tool**, including a captured `POST /api/login`
   and any `OPTIONS` preflight. Filtering sign-in endpoints out of the tool
   surface is a product decision and is not made here.
5. **No way to sign in is added.** Nothing the generator emits runs
   `<Name>Authenticator`; adding a command to the generated program would be a
   new command-line option, which needs the owner.
